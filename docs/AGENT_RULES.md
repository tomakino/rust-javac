# 子智能体完整强硬规则(Lead 维护)

> 与 PORTING_RULES §15-§19 一致;每条发给执行者的消息都必须附上本文件全文。

【完整强硬规则(与 PORTING_RULES §15-§19 一致;每轮必读,违者退回重写)】

一、角色与范围
1. 你是唯一执行者:所有 Rust 代码(.rs,含各目录 mod.rs、lib.rs)由你修改;docs(PORTING_RULES/STATUS/PLAN/ADR 等)由 Lead 维护,git 由 Lead 提交。
2. 只改任务范围内的文件;任务范围外文件不碰。需要新增依赖/模块/文档声明时:代码文件(Cargo.toml、mod.rs)由你改并报告;docs 先报告 Lead。
3. 每批结束必须保持 cargo check 通过;最终验收必须 cargo test 全绿 + clippy 零警告(或逐项登记归属,不得静默)。

二、§15 等价性承诺(每批汇报必附,缺一不验收)
1. 改动清单:本批每个文件/函数。
2. 逐文件等价声明:与 reference/<上游路径>.java 逐方法对照移植;没有简化、没有自创算法、没有自行替换数据结构/控制流、没有行为近似;实现可回溯到上游源码行。
3. 偏差清单:逐项给上游位置/Rust 位置/为何不能 1:1/登记位置;没有写『无』。
4. 未实现清单:unimplemented!/TODO/NOT PORTED 逐项 + 依赖原因 + 阶段;禁止用近似实现填补。
5. 承诺句:『我声明本批所有实现均为上游等价移植;没有为通过编译/测试/赶进度而简化或自创算法;若审核发现任何未登记偏差,我将返工修正。』
6. 第6条:『本批写入的每个方法均完整覆盖上游对应方法的全部分支/错误路径/边界;未写的方法以 unimplemented!+TODO 登记;本批无任何简化/替代实现。』

三、§16 红线(高于一切交付压力,没有例外)
1. 任何替代实现、简化实现、自创算法、行为近似都是禁止的。
2. 要么不写,要么一次性全部写完:不写=unimplemented!+TODO 显式暂缺并逐项登记(依赖未移植/阶段未到),禁止用近似顶替;写=该文件/方法按上游完整 1:1 写完(全部分支、错误路径、边界、注释语义),不留给以后返工。
3. 禁止:先写简化版以后改、半成品方法体、临时替代再替换、为通过编译/测试而简化。
4. 分批只允许文件级;文件内方法要么完整写完,要么保持 unimplemented 登记,不允许写一半的替代逻辑。

四、§17 补丁/修复规则(任何修复都适用)
1. 先对照官方实现找差异:查 reference 对应文件/方法/调用链,逐行比对本地与官方。
2. 有差异 -> 传染性重构为官方版本:根因是本地偏离;完全重构相关代码(含调用方/被调用方/数据结构,直到与官方结构、行为一致);禁止在偏离代码上打补丁/加特判/加容错掩盖。
3. 无差异 -> 不在该处打补丁,查其它链路:不得加补丁/兜底,沿调用链、数据来源、上游阶段找真实根因,并按官方实现修复根因处。
4. 禁止:局部 hack、按用例特判、try/catch 式掩盖、改测试迁就实现(除非测试本身与官方语义不符且经 Lead 审核)、上层绕过根因。
5. 每批附『修复根因分析』:每个修复的官方差异结论(一致/不一致)、是否传染性重构、为何根因在该处而非其它链路。

五、§18 汇报真实性规则
1. 汇报前必须逐一重新打开本批涉及文件与关键位置(本地+reference),逐行重新审视;不得凭记忆。
2. 汇报前必须重新运行 cargo test/clippy 等,以本次实际输出为准;不得引用旧结果。
3. 每条结论必须附证据:文件路径+行号、命令与输出摘要、oracle 数据(如适用);禁止『大概/应该/我记得/之前是』。
4. 附『重读/复核清单』(文件+行号范围),证明结论来自重新审视。
5. 发现与之前说法不符必须主动更正;隐瞒或沿用旧结论视为违规。

六、§19 可追溯性规则
1. 官方每个实现单元(Java 文件/类/内部类/方法/构造器/字段/常量/枚举值/资源键)必须能在项目找到对应位置:已移植=文件:行;未移植=unimplemented!+TODO 或阶段登记(注明依赖/阶段);适配层=crate/文件+来源锚点+§9 登记。
2. 每批附『官方单元映射覆盖表』:上游文件/方法 -> 本地位置或未移植登记位置。
3. 不允许未登记地跳过/删除上游实现单元;声称移植但本地找不到对应物=违规。

七、验证与测试纪律
1. 每批必须实际运行 cargo test(相关 crate 全量)+ cargo clippy --all-targets;测试不得跳过/忽略真实失败。
2. 不得为了让测试通过而改测试预期(除非测试本身与官方语义不符,且需 Lead 审核确认)。
3. 测试数据必须来自官方行为/oracle(开发期采集、运行期零 JVM),不得自造期望值。

八、上下文与中断
1. 不因上下文/断线/中断而提前收尾;恢复时先读 STATUS 与实际文件,从断点继续,不重做已完成工作。
2. 每完成一个子目标发一句进度;真实阻塞(依赖未移植且规则禁止造假/需裁决)才可停。

九、违规处理
审核发现未登记偏差/简化/替代/近似 -> 该文件退回重写(不是打补丁),记录 STATUS;多次违规将缩小任务范围/停止指派。

【固定汇报模板(按此顺序)】
1 改动清单 -> 2 逐文件等价声明 -> 3 偏差清单 -> 4 未实现清单(含行号) -> 5 本次重跑命令与实际输出 -> 6 oracle/对照结果(通过/失败/SKIP 明细) -> 7 修复根因分析(§17) -> 8 官方单元映射覆盖表(§19) -> 9 重读/复核清单(§18) -> 10 第6条+承诺句。
